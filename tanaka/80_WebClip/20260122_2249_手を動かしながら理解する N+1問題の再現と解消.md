## はじめに

`N+1` の問題についてDB関連のトピックでたまに耳にします。  
`N+1` があるとアプリのパフォーマンスが落ちてしまうのはなんとなくはわかっていても自分の言葉で説明しようとすると、うまいこといえないです。以下のような理解の程度です。

- 触ってみる前：
	- `覚えてた内容` ：1回クエリを発行してその後取得した各データにつきN回のクエリを発行する。その結果1+N回のクエリを発行することになり、取得データが増えるにつれクエリのレスポンスが帰ってくるのが遅くなる。アプリケーションのパフォーマンスが落ちることになる
	- `対策` ：たしかJOINを使って1回のクエリでデータを取り切るようにする

これはその課題に直面したことがないからかなと思いました。  
なので今回小規模な `N+1` を再現して触ってみることにしました。技術面接でもよく聞かれる内容かと思います。

Claude Codeと一緒に進めていきます。簡単な検証環境はサクッと作ってしまえると思います。

## N+1問題とは？

N+1問題とは1つの親となるようなデータを取得した後、その関連データをN回のクエリで取得してしまうパフォーマンス問題です。

下記のクエリだと最初にユーザ一覧を取得して、その後ユーザ1人1人の投稿データをN回取得しています。  
結果、ユーザーが1000人いれば1001クエリ、10000人いれば10001クエリのように線形にクエリの実行数が増加してしまいます。

- 例：「全ユーザーとその投稿一覧を表示したい」場合

```sql
1回目: SELECT * FROM users;                          -- 1クエリ（ユーザー5件取得）
2回目: SELECT * FROM posts WHERE user_id = 1;        -- User_Aの投稿
3回目: SELECT * FROM posts WHERE user_id = 2;        -- User_Bの投稿
4回目: SELECT * FROM posts WHERE user_id = 3;        -- User_Cの投稿
5回目: SELECT * FROM posts WHERE user_id = 4;        -- User_Dの投稿
6回目: SELECT * FROM posts WHERE user_id = 5;        -- User_Eの投稿
                                                     -- 合計: 1 + 5 = 6クエリ
```

クエリの説明

```sql
1回目: SELECT * FROM users;
```

`users` テーブルから全ユーザーを取得する。結果にはユーザ1人1人を識別するユーザーIDが含まれるイメージです。

```sql
2回目: SELECT * FROM posts WHERE user_id = 1;        -- User_Aの投稿
3回目: SELECT * FROM posts WHERE user_id = 2;        -- User_Bの投稿
4回目: SELECT * FROM posts WHERE user_id = 3;        -- User_Cの投稿
5回目: SELECT * FROM posts WHERE user_id = 4;        -- User_Dの投稿
6回目: SELECT * FROM posts WHERE user_id = 5;        -- User_Eの投稿
```

`posts` テーブルから各ユーザーの投稿を取得する。1回目で取得したユーザーIDごとにクエリを発行している。

| カラム名 | 型 | 説明 |

### テーブル作成

```sql
-- usersテーブル
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- postsテーブル
CREATE TABLE posts (
    id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    title VARCHAR(200) NOT NULL,
    body TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

-- インデックス作成
CREATE INDEX idx_posts_user_id ON posts(user_id);
```

SQLの意味

- `AUTO_INCREMENT PRIMARY KEY` ：AUTO\_INCREMENT 属性でプライマリキーに一意の識別子を生成します。レコード追加時にidを指定しなくても自動で1, 2, 3...と振られるイメージです
- `NOT NULL` ：NULLを許可しない制約。必須項目になります
- `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` ：現在のタイムスタンプをデフォルト値に設定
- `FOREIGN KEY (user_id) REFERENCES users(id)` ：外部キー制約。今回のpostテーブル作成のクエリでは、postsテーブルのuser\_idは、usersテーブルに存在するidしか入れられないように設定
- `CREATE INDEX idx_posts_user_id ON posts(user_id)` ：user\_id カラムにインデックスを作成する
	- もしこのindexがなかったら？：posts テーブルでは `user_id` が頻繁に WHERE 句や JOIN 条件に使われるはずのため、条件に合う行を探す際に全件スキャンが発生する。行数が増えるほどクエリが遅くなってしまう（O(n)の線形探索）。
	- インデックスを貼るとどうなるか？：MySQL（InnoDB）では B-tree（B+tree）構造のインデックスが使われるため、インデックス探索のコストは O(log n) 程度となり、全件スキャンを避けることができる
- 参考：
	- [https://dev.mysql.com/doc/refman/8.0/ja/example-auto-increment.html](https://dev.mysql.com/doc/refman/8.0/ja/example-auto-increment.html)
	- [https://dev.mysql.com/doc/refman/8.0/ja/timestamp-initialization.html](https://dev.mysql.com/doc/refman/8.0/ja/timestamp-initialization.html)
	- [https://dev.mysql.com/doc/refman/8.0/ja/data-type-defaults.html](https://dev.mysql.com/doc/refman/8.0/ja/data-type-defaults.html)
	- [https://www.ye-p.co.jp/node/360](https://www.ye-p.co.jp/node/360)

SQLの意味

	- 例：User\_A（id=1）の投稿はuser\_id=1になる。

## N+1問題を再現するPythonスクリプト

[pymysql](https://pypi.org/project/PyMySQL/) を用いて MySQL に接続し、1 回のクエリでユーザー一覧を取得します。  
その後for文のループ内で各ユーザーの投稿を取得します。全体としてN+1が発生するコードです。

```python
import pymysql

query_count = 0

def execute_query(cursor, sql, description=""):
    """クエリを実行し、カウントを増やす"""
    global query_count
    query_count += 1
    print(f"\n[Query #{query_count}] {description}")
    print(f"  SQL: {sql}")
    cursor.execute(sql)
    return cursor.fetchall()

def main():
    global query_count

    # MySQLに接続
    connection = pymysql.connect(
        host='localhost',  # ループバックアドレス（自分のPC）
        port=3306,
        user='root',
        password='password',
        database='n1_demo',
        cursorclass=pymysql.cursors.DictCursor
    )

    print("=" * 60)
    print("N+1問題の再現")
    print("=" * 60)

    try:
        with connection.cursor() as cursor:
            # ① 全ユーザーを取得（1回のクエリ）
            users = execute_query(
                cursor,
                "SELECT * FROM users",
                "全ユーザーを取得"
            )

            print(f"\n  → {len(users)}件のユーザーを取得")

            # ② 各ユーザーごとに投稿を取得（N回のクエリ）
            print("\n" + "-" * 60)
            print("各ユーザーの投稿をループで取得（ここがN+1問題の原因）")
            print("-" * 60)

            for user in users:
                posts = execute_query(
                    cursor,
                    f"SELECT * FROM posts WHERE user_id = {user['id']}",
                    f"{user['name']}の投稿を取得"
                )
                print(f"  → {len(posts)}件の投稿")

        # 結果サマリー
        print("\n" + "=" * 60)
        print("結果サマリー")
        print("=" * 60)
        print(f"ユーザー数: {len(users)}人")
        print(f"発行されたクエリ数: {query_count}回")
        print(f"内訳: 1回（ユーザー取得） + {len(users)}回（各ユーザーの投稿取得）")

    finally:
        connection.close()

if __name__ == "__main__":
    main()
```

## ゴール

上記で取得した情報は下記の2つです。

1. ユーザー情報（users）
2. 各ユーザーの投稿情報（posts）

この2つを取得しつつ、N+1 問題を発生させずにクエリ回数を少なく抑えることがゴールです。

以降では、この同じ目的に対して、JOIN / IN 句 / サブクエリという異なるアプローチを試していきます。

## N+1の解消

３つのパターンを試してみます。

## パターン1: JOINを使った方法

### 考え方

JOINを使って、1回のクエリでユーザーと投稿を同時に取得します。

```sql
SELECT
    users.id as user_id,
    users.name as user_name,
    posts.id as post_id,
    posts.title as post_title
FROM users
LEFT JOIN posts ON users.id = posts.user_id
ORDER BY users.id, posts.id
```

#### LEFT JOIN の動作

- `FROM users` → usersテーブルを基準にする
- `LEFT JOIN posts ON users.id = posts.user_id` → usersのidとpostsのuser\_idが一致する行を結合
- usersテーブルの右側に、対応するpostsテーブルの投稿情報がくっつく

### 実行結果

```

  SQL: SELECT users.id as user_id, users.name as user_name,
       posts.id as post_id, posts.title as post_title
       FROM users
       LEFT JOIN posts ON users.id = posts.user_id
       ORDER BY users.id, posts.id

取得したデータ:
------------------------------------------------------------
user_id    user_name    post_id    post_title
------------------------------------------------------------
1          User_A       1          Post_A1
1          User_A       2          Post_A2
1          User_A       3          Post_A3
2          User_B       4          Post_B1
2          User_B       5          Post_B2
3          User_C       6          Post_C1
3          User_C       7          Post_C2
3          User_C       8          Post_C3
3          User_C       9          Post_C4
4          User_D       10         Post_D1
5          User_E       11         Post_E1
5          User_E       12         Post_E2

発行されたクエリ数: 1回
```

### JOINの特徴

| 項目 | 内容 |
| --- | --- |
| クエリ数 | 1回 |
| 取得行数 | 12行（投稿数分だけ行が増える） |
| その他メモ | ユーザー情報が投稿の数だけ重複して出現する |
| アプリ側の処理 | 同じ `user_id` の行をグループ化する必要がある |

## パターン2: IN句を使った取得

### 考え方

N+1問題では、各ユーザーごとに1回ずつクエリを発行していました。

```sql
SELECT * FROM posts WHERE user_id = 1;
SELECT * FROM posts WHERE user_id = 2;
SELECT * FROM posts WHERE user_id = 3;
SELECT * FROM posts WHERE user_id = 4;
SELECT * FROM posts WHERE user_id = 5;
```

違いは `user_id = ○` の数値だけなので、IN句を使えば1回にまとめられそうです。

```sql
SELECT * FROM posts WHERE user_id IN (1, 2, 3, 4, 5);
```

### 実行結果

```
[Query #1] 全ユーザーを取得
  SQL: SELECT * FROM users
  → ユーザーIDリスト: [1, 2, 3, 4, 5]

[Query #2] IN句で全投稿を一括取得
  SQL: SELECT * FROM posts WHERE user_id IN (1, 2, 3, 4, 5)
  → 12件の投稿を取得

発行されたクエリ数: 2回
```

### IN句の特徴

| 項目 | 内容 |
| --- | --- |
| クエリ数 | 2回（ユーザー取得 + 投稿一括取得） |
| 取得行数 | users: 5行、posts: 12行（別々に取得） |
| その他メモ | usersとpostsを別々のテーブルとして取得 |
| アプリ側の処理 | 投稿を `user_id` でグループ化する必要がある |

## パターン3: IN句をSQL内で完結させるためにサブクエリを使う方法

### 考え方

パターン2でやった方法に近いですがサブクエリを活用した方法です。  
IN句の中に対象のユーザを取得するためのクエリをサブクエリとして埋め込んでいます。  
サブクエリ自体が N+1 問題を解消するわけではなく、「クエリを1回にまとめて取得している」ことがN+1 を防いでいるポイントです。

サブクエリとは

- サブクエリとは

> サブクエリーは、別のステートメント内の SELECT ステートメントです。  
> 参考： [https://dev.mysql.com/doc/refman/8.0/ja/subqueries.html](https://dev.mysql.com/doc/refman/8.0/ja/subqueries.html)

- ステートメントとは  
	SQLを使ったデータベースに対する指示文  
	参考： [https://wa3.i-3-i.info/word110808.html](https://wa3.i-3-i.info/word110808.html)

```sql
SELECT * FROM posts
WHERE user_id IN (SELECT id FROM users);
                  ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
                  これがサブクエリ（内側のクエリ）
```

**処理のイメージ：**

1. 内側のクエリで users.id の一覧を取得する → `SELECT id FROM users` → 結果: `1, 2, 3, 4, 5`
2. その結果を使って posts を絞り込む → `SELECT * FROM posts WHERE user_id IN (1, 2, 3, 4, 5)`

パターン2のIN句ではアプリ側でIDリストを作るようなイメージですが、サブクエリではそこをSQL内で完結します。

### パターン2との違い

| 観点 | パターン2（IN句） | パターン3（サブクエリ） |
| --- | --- | --- |
| IDリストの管理 | アプリ側で配列を作成 | SQL内で完結 |
| 柔軟性 | IDを動的に操作しやすい | 条件追加はサブクエリ内で行う |

### 実行結果

```
[Query #1] サブクエリで全投稿を取得
  SQL: SELECT * FROM posts
       WHERE user_id IN (SELECT id FROM users)
  → 12件の投稿を取得

[Query #2] ユーザー情報を取得（必要な場合）
  SQL: SELECT * FROM users

発行されたクエリ数: 2回
（ユーザー情報と投稿情報を別々のクエリで取得）
```

### サブクエリの特徴

| 項目 | 内容 |
| --- | --- |
| クエリ数 | 2回（users と posts を別クエリで取得） |
| 特徴 | IDリスト作成をSQL内で完結できる |
| 注意点 | ユーザー情報は取れないので、必要なら別途取得 |

## 各パターンの比較

## クエリ数の比較

| パターン | クエリ数 | 備考 |
| --- | --- | --- |
| N+1問題 | 6回 | ユーザー数に比例して増加 |
| パターン1（JOIN） | 1回 | クエリの実行結果、データが重複することがあった |
| パターン2（IN句） | 2回 | データを別々に取得できる |
| パターン3（サブクエリ） | 2回 | users と posts を別クエリで取得 |

## 使い分けの目安

| 目的 | おすすめ | 理由 |
| --- | --- | --- |
| クエリ回数を最小にしたい | **JOIN** | 1回のクエリで users と posts を同時に取得できる |
| users と posts を別々に取得したい | **IN句** | ユーザーIDをアプリ側で管理でき、処理を分けやすい |
| users と posts を別々に取得したい（ID取得をSQL内で完結させたい） | **サブクエリ** | ユーザーIDの取得をサブクエリに閉じ込められる |

## まとめ

今回、実際に N+1 問題を再現し、3つの解消パターンを試してみた結果、どのアプローチでもクエリの実行回数を「6回 → 1〜2回」に削減できることを確認できました。

N+1 問題は、「ループの中で関連データを1件ずつ取得している」というコード構造が原因になりやすいことを、実際のクエリ発行回数と実行結果を通して理解できました。

触ってみる前は、

> - N+1 問題はクエリの実行回数が増えてパフォーマンスが悪くなること
> - JOIN を使えば解消できる

といった断片的な知識として理解していましたが、今回検証してみたことで次のように整理できました。

- N+1問題とは、本来まとめて取得できる関連データをループによって分割取得してしまうことが原因になりやすい
- JOIN・IN 句・サブクエリはいずれも、データ取得の単位をまとめるための手段として活用できる

実務では、取得したいデータの形や件数、アプリ側での扱いやすさを考慮しながら設計と開発を進めていきたいです。
