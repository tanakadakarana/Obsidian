- 私が書いた原文を AI に表現をブラッシュアップしてもらっています

エンジニアなら誰しも、「これ自動化できそうだな」と思い立って、作業を横に置いてツール作りに没頭してしまう瞬間があると思います。

私も先日、ドキュメント内のパス参照をCIで自動更新する仕組みを、2時間かけて実装しました。  
でも、そのコードは一度もまともに動くことなく、わずか1週間で私の手によって削除されました。

「せっかく作ったのにもったいない」と思わず、なぜ消したほうがマシだったのか、その判断基準をメモしておきます。

## 事例1: パス自動置換が「負債」になった理由

私が作ったのは、ドキュメント内の `{PATH:key}` というプレースホルダーをCI上で実パスに置換して、さらにそれをGitにコミットし直すという仕組みでした。

狙いとしては、パス管理を一元化したかったんです。たとえば `docs/drafts/` というパスを10箇所のドキュメントで使っていて、ディレクトリ構成が変わったときに全部手動で直すのが面倒だと感じていました。

だから、「YAMLにパスを定義して、ドキュメントにはプレースホルダーを書いておけば、CIが自動で置換してくれる」という仕組みを作りました。

### 問題1: 無限ループ

ところが、いざ動かしてみると、

1. CIが置換してコミットする。
2. そのコミットに対して、またCIが走る。
3. プレースホルダーが消えているのでエラーになる。  
	という負のループに陥りました。

CIが作ったコミットにはプレースホルダーが残っていないので、次のCI実行時に「プレースホルダーが見つからない」とエラーになります。

### 問題2: Git履歴の汚染

さらに、毎回CIがコミットを作るので、Git履歴がノイズだらけになりました。`git log` を見ても、「自動置換: パスを更新」というコミットが延々と並ぶだけで、本質的な変更が埋もれてしまいます。

### 問題3: レビュー不能

PRを出しても、「このコミットはCIが自動生成したものです」と説明する羽目になり、レビュアーは混乱します。人間が書いた変更とCIが書いた変更が混在していて、どこまでレビューすればいいのか分かりません。

この「CIの挙動を監視して、手動で修正する」という作業は、自動化したかったはずの手順よりも、ずっと面倒で不毛なものでした。

## 事例2: Zennリポジトリで3,000行を削減した

別のリポジトリでも同じ失敗をしていました。

Zenn記事を管理するリポジトリで、「便利そう」と思って作った自動化が積み重なり、気づけば毎回失敗するCIワークフロー、誰も使っていないスクリプト、運用と合わなくなった設定ファイルだらけになっていました。

### 削除したもの

| 機能 | 廃止理由 |
| --- | --- |
| 公開状態チェックCI | 記事アーカイブを別リポジトリに移行した結果、毎回警告が出て無視する習慣がついた |
| Gitフックによるブランチ保護 | 緊急時に直接pushしたい場面があり、結局回避されるだけだった |
| AI学習用サンプルデータ | 別システムで品質判定の仕組みを作ったため不要に |
| テンプレート群 | AIがfront matterを自動生成するようになり使わなくなった |

### 結果

- **削除前**: 約6,000行、56ファイル
- **削除後**: 約2,700行、37ファイル
- **差分**: 約3,300行、19ファイル削減

行数が減った以上に、「毎回失敗するCIを見て見ぬふりする罪悪感」から解放されたのが一番の収穫でした。

### なぜ積み重なったのか

どれも理屈は正しかった。公開状態を自動チェックできたら便利、公開ブランチを保護しておいた方が安全、サンプルがあればAIが学習しやすい。

でも実際に困っていたかと聞かれると、そうでもない。

「せっかく作ったのにもったいない」「いつか使うかもしれない」という心理が、使われないコードを延命させていました。クローゼットの奥に眠っている「いつか着るかも」の服と同じです。

## 損益分岐点を計算してみた

削除した後に冷静に計算してみましたが、そもそもこの自動化は投資に見合っていませんでした。

### 実際にかかった時間

- **自動化スクリプトの開発**: 2時間
- **CIの設定とテスト**: 1時間
- **無限ループのデバッグ**: 1.5時間
- **Git履歴のクリーンアップ**: 0.5時間
- **合計**: 5時間

### 手動でやった場合のコスト

- **頻度**: 月1回、パスを変更するかどうか
- **作業時間**: `sed` でまとめて置換するだけなので5分
- **年間コスト**: 60分

つまり、5年使い続けて、ようやく元が取れる計算です。

しかも、5年後にリポジトリの構造が変わっていない保証はありません。おそらく、ディレクトリ構成は1年以内に何度か変わるでしょうし、そのたびにYAMLを更新して、プレースホルダーも見直して、という作業が発生します。

私は、「起こるかどうかも分からない不便」のために、今この瞬間の貴重な5時間をドブに捨てていたことになります。

### なぜ作る前に計算しなかったのか

振り返ってみると、「自動化できる = 自動化すべき」という思い込みがありました。

「エンジニアたるもの、手作業を自動化するのが美徳だ」という価値観が、判断を狂わせていたんです。実際には、自動化はコストであり、投資対効果を冷静に見極める必要があるのに、です。

## 自動化を自制するための基準

今の私は、何かを自動化したくなったら、以下の3つを自分に問いかけています。

### 1\. 週1回以上、その作業に不便を感じているか？

月1回なら、手動でやったほうが早いです。

「たまにやる作業」を自動化すると、スクリプトの使い方を忘れます。そして、使い方を思い出すためにドキュメントを読んだり、過去のログを漁ったりする時間が発生します。これは本末転倒です。

たまにしかやらない作業は、「手順書をREADMEに書いておく」だけで十分です。そして、実行するときはコマンドを一つ一つ叩けばいいんです。

### 2\. 手動だと5分以上かかるか？

5分以内で終わる作業を自動化しても、開発時間のほうが長くつきます。

しかも、自動化スクリプトは「エラーハンドリング」「ログ出力」「引数の検証」など、手動作業では不要な部分まで実装する必要があります。たとえば、手動なら「ファイルがなかったら自分で気づいて作る」で済むところを、スクリプトでは「ファイルの存在チェック → エラーメッセージ → 自動作成するか確認」と複雑になります。

### 3\. そのスクリプトは、保守が必要にならないか？

自動化コードも保守対象です。

たとえば、APIのバージョンが上がったら、スクリプトも修正が必要になります。ディレクトリ構成が変わったら、パスの書き換えが必要です。依存ライブラリが非推奨になったら、リプレイスが必要です。

「一度書いたら終わり」という自動化はほとんどありません。むしろ、「作った瞬間から保守コストが発生する」と考えたほうが正確です。

## YAGNI原則とは

YAGNI = **You Aren't Gonna Need It**（それは必要にならない）

Extreme Programmingから生まれた原則で、「必要になるまで実装するな」という意味です。

自動化も同じで、「今すぐ必要でない自動化は作るな」ということです。

「将来パスが変わるかもしれない」という仮定で自動化を作っても、その「将来」が来ないかもしれません。来たとしても、そのときに `sed` で一括置換すれば5分で終わる話です。

## 自動化すべきかの判断フロー

自動化を検討する際は、以下のフローで判断します。

```
1. その作業は何回発生するか？
   └─ 1-2回 → 手動でやる
   └─ 週1回以上 → 2へ

2. 1回の作業時間は？
   └─ 5分以下 → 手動でやる
   └─ 30分以上 → 3へ

3. 自動化の開発時間は？
   └─ 作業時間 × 予想回数 より大きい → 手動でやる
   └─ 小さい → 自動化を検討

4. 保守コストは？
   └─ 環境依存、外部API依存 → 慎重に判断
   └─ シンプルなスクリプト → 自動化OK
```

私の場合は、フロー1で「月1回」だったので、そもそも自動化すべきではなかったのです。

## 「必要になってから実装する」の意味

YAGNIは「永遠に実装するな」ではありません。

**実際の痛みを確認してから実装する**という意味です。

### 悪い例

「いつかパス変更があるかもしれないから、今のうちに自動化しておこう」

→ 予測に基づく実装。必要性が不明確。

### 良い例

「先月もパス変更で30分かかった。今月も同じ作業が発生した。来月も発生しそうだ。自動化しよう」

→ 実際の痛みに基づく実装。必要性が明確。

## 削除してから見えたこと

この自動化を削除した後、実際にパスを変更する機会が2回ありました。

1回目は、`scripts/` を `scripts/ci/` に変更したとき。  
2回目は、`old_articles/` を `archive/old_articles/` に移動したとき。

どちらも、以下の手順で終わりました。

```
# 1. 該当ファイルを検索
grep -r "scripts/" .

# 2. sedで一括置換
find . -type f -name "*.md" -exec sed -i '' 's|scripts/|scripts/ci/|g' {} +
```

所要時間は、それぞれ3分程度です。

自動化を作っていたら、YAMLを更新して、CIを実行して、結果を確認して、という手順が必要でした。むしろ、手動のほうが速かったです。

### 「自動化の負債」を抱えなくなった

削除して一番よかったのは、「このスクリプト、まだ動くかな？」という不安から解放されたことです。

自動化スクリプトがあると、何か変更するたびに「このスクリプトに影響ないか？」と気にする必要があります。CIが失敗したら、「スクリプトのバグか、設定の問題か、それとも自分のコードが悪いのか？」と切り分けが必要です。

削除したことで、そういった認知負荷がゼロになりました。

## 自動化は「負債」だと認識する

自動化は、便利なツールである反面、保守コストを生む負債でもあります。

「自動化すれば楽になる」と思いがちですが、実際には「楽になる部分」と「複雑になる部分」の両方があります。そして、複雑になる部分のコストが、楽になる部分の利益を上回ることは珍しくありません。

私の場合、以下のようなコストが発生していました。

- スクリプトの保守（ライブラリのアップデート、バグ修正）
- CIの設定メンテナンス（GitHub Actionsのバージョンアップ対応）
- ドキュメントの更新（使い方が変わったら説明も変える）
- 他の人への説明（「このコミットはCIが自動生成したものです」）

これらのコストは、「自動化すれば手間が減る」という期待に含まれていませんでした。

結局、私が2時間かけてやりたかったことは、`sed` コマンド一行で済む話でした。  
たまに発生する数カ所の置換なら、コマンドを叩くか、AIに「これ置換して」と言うだけで5秒で終わります。

「自動化しなきゃ」という強迫観念で複雑な仕組みを作るより、「その都度、一番楽な方法で片付ける」ほうが、開発全体の効率は上がるんだろうな、と痛感しました。

## 自動化の誘惑に負けないために

自動化を判断する際のチェックリスト：

1. **頻度を確認する**：週1回未満なら手動で十分なことが多い
2. **投資回収期間を計算する**：開発時間 ÷ (節約時間 × 頻度)
3. **保守コストを考慮する**：作ったら終わりではない
4. **痛みを確認する**：「あったら便利」ではなく「ないと困る」か

エンジニアにとって自動化は魅力的です。しかし、**5分の手作業を自動化するために2時間を投資する**前に、本当に必要かを立ち止まって考えましょう。

YAGNI——それは必要にならない。
